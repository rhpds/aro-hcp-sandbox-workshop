= Install Kata, Break It, Fix It

== Value Proposition

Installing the Sandboxed Containers Operator is necessary but not sufficient. The Kata runtime does not activate until a `KataConfig` resource tells the operator which nodes to configure. That configuration step is deceptively easy to get wrong: a single label mismatch between the `kataConfigPoolSelector` in KataConfig and the label applied to the Kata NodePool in Module 2 causes the operator to proceed silently — no error, no warning, zero nodes configured.

This module closes the installation loop. You apply KataConfig with careful attention to the selector, watch the MachineConfigPool update cycle in real time, and verify the result at two layers: the cluster-level `kata` RuntimeClass and the containerd runtime registry on the node itself.

Then you deliberately break it. The most common Sandboxed Containers admission failure seen in the field is a `Forbidden` error caused by missing SCC configuration. You reproduce it, trace it with `oc describe` and `oc adm policy who-can`, and fix it. The module closes with a discussion of production-appropriate SCC assignment strategy.

== Learning Objectives

By the end of this module you will be able to:

* Configure KataConfig with a `kataConfigPoolSelector` that correctly matches the Kata NodePool node label from Module 2
* Observe the MachineConfigPool update cycle as nodes cordon, drain, reboot, and return to Ready state
* Verify Kata installation at two layers: the `kata` RuntimeClass in the cluster and the kata handler in containerd's runtime registry
* Reproduce and trace the most common Kata admission failure using pod events and `oc adm policy who-can`
* Fix the admission failure by granting the Kata SCC to the service account

== Section 1 — Apply KataConfig

=== The kataConfigPoolSelector

KataConfig does not install Kata binaries on every node — it installs them only on nodes that match the `kataConfigPoolSelector`. The selector is a standard Kubernetes label selector. If it does not exactly match the label applied to the Kata NodePool nodes in Module 2, the operator proceeds with zero nodes configured and reports no error.

Confirm the label is present on the Kata nodes before applying KataConfig:

[source,bash,role=execute]
----
oc get nodes -l node-role.kubernetes.io/kata= \
  -o custom-columns=NAME:.metadata.name,INSTANCE:.metadata.labels."node\.kubernetes\.io/instance-type"
----

Both `Standard_D4s_v5` nodes should appear. If this returns nothing, the label from Module 2 was not applied correctly — stop and re-apply it before continuing.

=== Configure ACR Registry Credentials

The Sandboxed Containers Operator reads the OpenShift release image manifest to locate the Kata extension payload. In ARO HCP, release images are mirrored to a private Azure Container Registry (`arohcpocpprod.azurecr.io`). The operator's internal HTTP client reads credentials from the filesystem — not from Kubernetes pull secrets — so those credentials must be explicitly mounted into the operator pod before KataConfig will work.

. Extract the ACR credentials from the cluster pull secret and create a Docker config secret in the operator namespace:
+
[source,bash,role=execute]
----
oc get secret pull-secret -n openshift-config \
  -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d | \
  jq '{"auths": {"arohcpocpprod.azurecr.io": .auths["arohcpocpprod.azurecr.io"]}}' \
  > /tmp/acr-config.json

oc create secret generic acr-docker-config \
  --from-file=config.json=/tmp/acr-config.json \
  -n openshift-sandboxed-containers-operator \
  --dry-run=client -o yaml | oc apply -f -
----

. Capture the controller-manager container name and patch the deployment to mount the credentials:
+
[source,bash,role=execute]
----
CONTAINER=$(oc get deployment controller-manager \
  -n openshift-sandboxed-containers-operator \
  -o jsonpath='{.spec.template.spec.containers[0].name}')

oc patch deployment controller-manager \
  -n openshift-sandboxed-containers-operator \
  --type=strategic -p "{
  \"spec\": {
    \"template\": {
      \"spec\": {
        \"volumes\": [{\"name\": \"acr-docker-config\", \"secret\": {\"secretName\": \"acr-docker-config\"}}],
        \"containers\": [{
          \"name\": \"${CONTAINER}\",
          \"env\": [{\"name\": \"DOCKER_CONFIG\", \"value\": \"/tmp/docker-cfg\"}],
          \"volumeMounts\": [{\"name\": \"acr-docker-config\", \"mountPath\": \"/tmp/docker-cfg\", \"readOnly\": true}]
        }]
      }
    }
  }
}"
----

. Wait for the operator to roll out with the new credentials:
+
[source,bash,role=execute]
----
oc rollout status deployment/controller-manager \
  -n openshift-sandboxed-containers-operator
----

[NOTE]
====
This step is specific to ARO HCP. The cluster's release images are mirrored to a private ACR that uses managed identity authentication at the node level. The operator's Go HTTP client cannot use managed identity — it reads credentials from `$DOCKER_CONFIG/config.json` on disk. Mounting the pull secret at that path gives the operator the Bearer token it needs to inspect the release image manifest and locate the Kata extension payload.
====

=== Apply KataConfig

. Apply the KataConfig resource, setting the `kataConfigPoolSelector` to match `node-role.kubernetes.io/kata`:
+
[source,bash,role=execute]
----
oc apply -f - <<'EOF'
apiVersion: kataconfiguration.openshift.io/v1
kind: KataConfig
metadata:
  name: example-kataconfig
spec:
  kataConfigPoolSelector:
    matchLabels:
      node-role.kubernetes.io/kata: ""
EOF
----

. Confirm the resource was created and note the status columns:
+
[source,bash,role=execute]
----
oc get kataconfig example-kataconfig
----
+
Expected output:
+
----
NAME                 INPROGRESS   COMPLETED   TOTAL   AGE
example-kataconfig                                    Xm
----
+
The three status columns track the MCO rollout as it runs:
+
* `INPROGRESS` — number of nodes currently being processed (cordoned, draining, or rebooting)
* `COMPLETED` — number of nodes that have finished installing Kata binaries and returned to Ready
* `TOTAL` — total number of nodes targeted by the `kataConfigPoolSelector`
+
All three are empty immediately after creation. They populate once the MCO begins cordoning the first node. If `TOTAL` remains empty after several minutes, the `kataConfigPoolSelector` matched zero nodes — verify the label with `oc get nodes -l node-role.kubernetes.io/kata=`.

[NOTE]
====
The `kataConfigPoolSelector` value `node-role.kubernetes.io/kata: ""` must be an exact match — same key, same value — as the label applied in Module 2. An empty string (`""`) is a valid label value in Kubernetes. If the selector uses any other value, KataConfig installs on zero nodes silently.
====

== Section 2 — Watch the Kata Installation Rollout

When KataConfig is applied, the Sandboxed Containers Operator installs Kata binaries onto each matching node in sequence: cordoning the node, draining workloads, rebooting, and returning the node to Ready state.

In ARO HCP, the MachineConfigPool API is not exposed to the customer — node configuration is managed internally by the service. Progress is tracked instead through the KataConfig status columns and the node state directly.

This cycle typically takes several minutes per node. Use two terminals to observe it in parallel.

=== Terminal 1 — Watch the KataConfig Status

. Watch the KataConfig status columns for progress:
+
[source,bash,role=execute]
----
oc get kataconfig example-kataconfig -w
----
+
As the rollout proceeds, the columns populate:
+
* `INPROGRESS` — number of nodes currently being processed
* `COMPLETED` — number of nodes with Kata binaries installed
* `TOTAL` — total number of nodes targeted
+
Wait for `COMPLETED` to equal `TOTAL` before continuing to Section 3. Press `Ctrl+C` once complete.

=== Terminal 2 — Watch the Kata Nodes

. In a second terminal, watch the Kata nodes directly:
+
[source,bash,role=execute]
----
oc get nodes -l node-role.kubernetes.io/kata= -w
----
+
Each Kata node will transition through:
+
* `Ready,SchedulingDisabled` — node cordoned, no new pods will be scheduled
* `NotReady,SchedulingDisabled` — node rebooting to apply the new configuration
* `Ready` — node returned to service with Kata binaries installed

[NOTE]
====
ARO HCP does not expose the `machineconfigpool` API — that resource belongs to the MachineConfig Operator (MCO) in self-managed OpenShift. In ARO HCP, node-level configuration is managed internally by the service. The KataConfig status columns (`INPROGRESS`, `COMPLETED`, `TOTAL`) are the authoritative progress indicator for Kata installation on ARO HCP.
====

=== While You Wait — Observe the Installation Internals

Each node reboot takes 5–8 minutes. Use this time to make the installation visible rather than waiting passively.

==== Watch the Operator DaemonSet

The Sandboxed Containers Operator creates a DaemonSet to push Kata binaries onto each matching node. Watch it come up:

[source,bash,role=execute]
----
oc get daemonset -n openshift-sandboxed-containers-operator -w
----

The DaemonSet rolls one pod per Kata node. Each pod handles the binary installation on its node and exits when done. This is how the operator delegates node-level work without needing direct host access.

==== Stream the Operator Logs

The controller-manager logs every step of the rollout:

[source,bash,role=execute]
----
oc logs deployment/controller-manager \
  -n openshift-sandboxed-containers-operator -f \
  | grep -iE "kata|node|install|daemon"
----

You will see the operator detecting the KataConfig, creating the DaemonSet, and tracking node progress. Press `Ctrl+C` when you are done observing.

==== Inspect the Node Before Kata Is Installed

Open a debug shell on a Kata node while it is still waiting to be processed. Capture the containerd runtime list — you will compare this to the same output in Section 3 after installation completes:

[source,bash,role=execute]
----
KATA_NODE=$(oc get nodes -l node-role.kubernetes.io/kata= \
  -o jsonpath='{.items[0].metadata.name}')

oc debug node/$KATA_NODE -- chroot /host \
  crictl info | grep -A 3 runtimes
----

The `kata` handler is absent. After Section 3's verification step, the same command will show the kata handler registered — making the before/after change concrete.

== Section 3 — Verify Kata Installation

Kata installation must be verified at two layers. A RuntimeClass present in the cluster confirms the API is registered. The kata handler present in containerd's runtime registry on the node confirms the binary is actually installed and usable.

=== Layer 1 — Cluster: RuntimeClass

. Confirm the `kata` RuntimeClass now exists:
+
[source,bash,role=execute]
----
oc get runtimeclass kata
----
+
Expected output:
+
----
NAME   HANDLER   AGE
kata   kata      Xm
----
+
The `HANDLER` value `kata` tells containerd which runtime binary to call when a pod requests this class. If this resource is absent, the MachineConfigPool rollout did not complete or the `kataConfigPoolSelector` matched zero nodes.

=== Layer 2 — Node: containerd Runtime Registry

. Capture a Kata node name:
+
[source,bash,role=execute]
----
KATA_NODE=$(oc get nodes -l node-role.kubernetes.io/kata= \
  -o jsonpath='{.items[0].metadata.name}')
echo $KATA_NODE
----

. Open a debug shell on the Kata node:
+
[source,bash,role=execute]
----
oc debug node/$KATA_NODE
----

. Inside the debug shell, inspect the containerd runtime registry:
+
[source,bash,role=execute]
----
chroot /host crictl info | grep -A 5 kata
----
+
The `kata` handler should appear in the `runtimes` section of the containerd configuration. If it is absent, the MachineConfig did not apply correctly on this node — check `oc get machineconfigpool kata` and look for degraded conditions.

. Exit the debug shell:
+
[source,bash,role=execute]
----
exit
----

== Section 4 — Break It: Trigger the Admission Failure

The most common Kata deployment error seen in the field is not a configuration error — it is an admission error. Pods requesting the `kata` runtime require elevated privileges to create the nested VM. Without the correct SCC grant, OpenShift's admission controller blocks the pod before it is ever scheduled.

=== Deploy a Kata Pod Without SCC

. Create a namespace for the test:
+
[source,bash,role=execute]
----
oc new-project kata-test
----

. Attempt to deploy a Kata pod without any SCC configuration:
+
[source,bash,role=execute]
----
oc apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: kata-test-pod
  namespace: kata-test
spec:
  runtimeClassName: kata
  tolerations:
  - key: kata
    value: "true"
    effect: NoSchedule
  containers:
  - name: ubi
    image: registry.access.redhat.com/ubi9/ubi-minimal
    command: ["sleep", "infinity"]
EOF
----

. Observe that the pod does not start:
+
[source,bash,role=execute]
----
oc get pod kata-test-pod -n kata-test
----

=== Trace the Failure

. Examine the pod events to locate the admission error:
+
[source,bash,role=execute]
----
oc describe pod kata-test-pod -n kata-test | grep -A 10 Events
----
+
The events section will contain a `Forbidden` message referencing the SCC policy. The pod was blocked at admission — it never reached the scheduler.

. Identify which service accounts currently have permission to use the Kata SCC:
+
[source,bash,role=execute]
----
oc adm policy who-can use scc kata-scc
----
+
The `default` service account in the `kata-test` namespace is not listed. The pod is running as `default` — it does not have the required SCC grant.

[NOTE]
====
This is the field failure pattern: the operator is installed, KataConfig is applied, the RuntimeClass exists — everything looks correct — but pods fail at admission. The `Forbidden` event and `oc adm policy who-can` are the two tools that immediately surface the root cause.
====

== Section 5 — Fix It: Grant the SCC

=== Grant the SCC to the Service Account

. Grant the Kata SCC to the `default` service account in the `kata-test` namespace:
+
[source,bash,role=execute]
----
oc adm policy add-scc-to-user kata-scc -z default -n kata-test
----

. Delete and re-apply the pod so it is evaluated under the new SCC grant:
+
[source,bash,role=execute]
----
oc delete pod kata-test-pod -n kata-test
oc apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: kata-test-pod
  namespace: kata-test
spec:
  runtimeClassName: kata
  tolerations:
  - key: kata
    value: "true"
    effect: NoSchedule
  containers:
  - name: ubi
    image: registry.access.redhat.com/ubi9/ubi-minimal
    command: ["sleep", "infinity"]
EOF
----

. Confirm the pod reaches `Running` state:
+
[source,bash,role=execute]
----
oc get pod kata-test-pod -n kata-test -w
----
+
Wait for `STATUS` to show `Running`, then press `Ctrl+C`.

=== Production Consideration: SCC Assignment Strategy

The fix above grants the `kata-scc` to the `default` service account. This works, but it means every pod in the `kata-test` namespace running as `default` now has Kata SCC privileges — including workloads that are not Kata pods.

For production environments:

* Create a dedicated service account for Kata workloads: `oc create serviceaccount kata-workloads -n <namespace>`
* Grant the SCC to that account only: `oc adm policy add-scc-to-user kata-scc -z kata-workloads -n <namespace>`
* Set `serviceAccountName: kata-workloads` in each Kata pod spec

This scopes the privilege grant precisely to workloads that require it, following the principle of least privilege. The `default` service account retains no Kata SCC grant.

== Summary

=== What You Learned

* **The `kataConfigPoolSelector` is the most common Kata misconfiguration.** A label mismatch causes zero nodes to be configured with no error output. Verify with `oc get nodes -l node-role.kubernetes.io/kata=` before applying KataConfig.
* **KataConfig tracks the rollout through status columns.** In ARO HCP, the `machineconfigpool` API is not exposed. Progress is visible in the `INPROGRESS`, `COMPLETED`, and `TOTAL` columns of `oc get kataconfig`. Each Kata node cordons, drains, reboots, and returns Ready as Kata binaries are installed.
* **Kata installation requires two-layer verification.** The `kata` RuntimeClass in the cluster proves the API is registered. The kata handler in the containerd runtime registry on the node proves the binary is installed. Both must be present for Kata pods to run.
* **The most common field admission failure is a missing SCC grant.** The pod is blocked at admission with a `Forbidden` event. `oc adm policy who-can use scc kata-scc` immediately surfaces which accounts have the grant — and confirms the one that does not.
* **SCC grants should follow least privilege.** Granting to the `default` service account is expedient but broad. A dedicated service account scoped to Kata workloads is the production-appropriate pattern.

=== Key Takeaways for Customer Conversations

*"KataConfig is installed but pods aren't using Kata — what's wrong?"*

Check the `kataConfigPoolSelector` first. Run `oc get nodes -l node-role.kubernetes.io/kata=` — if it returns nothing, the label either wasn't applied or doesn't match the selector exactly. KataConfig silently skips nodes whose labels don't match.

*"How do I know Kata is actually installed on the node and not just registered in the API?"*

Two-layer verification: `oc get runtimeclass kata` confirms the API object. Then `oc debug node/<kata-node>` and `chroot /host crictl info | grep kata` confirms the handler is registered in containerd's runtime registry. Both must pass before you trust that a Kata pod will run.

*"A customer's Kata pod gets a Forbidden error. What do I check?"*

Run `oc describe pod <name>` and look for the SCC message in events. Then `oc adm policy who-can use scc kata-scc` confirms which accounts have the grant. The fix is `oc adm policy add-scc-to-user kata-scc -z <serviceaccount> -n <namespace>`. Recommend a dedicated service account over granting to `default`.

*"Is rebooting nodes acceptable in a production ARO HCP cluster?"*

Yes — Kata installation performs a rolling reboot, one node at a time, with cordon and drain before each reboot. Workloads are rescheduled before the node goes down. The kata-nodepool has a NoSchedule taint, so only Kata workloads land there — those workloads are specifically designed for this node type and do not need to be migrated to other pools.
