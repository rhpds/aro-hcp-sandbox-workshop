== What You've Learned

  and confirming the absence of customer-managed master VMs, etcd disks, and control

* Scaled a worker NodePool and traced the resulting Azure VM provisioning through the

* Explored the Red Hat Build of Agent Sandbox and saw how `SandboxTemplate`,

  admins central control over AI agent isolation

== Key Takeaways

The control plane and the data plane have fundamentally different security boundaries in
ARO HCP. The absence of master VMs and etcd disks in your resource group is not an
oversight — it is the product. Red Hat manages that layer, Managed Identity and Workload
Identity replace static credentials, and your compliance team gets documented evidence
instead of contested assurances.

Kata Containers move the isolation boundary from namespace to kernel. A `runc` container
shares the host kernel; a `kata` pod runs inside a KVM guest VM. When you compared kernel
versions across host, runc pod, and kata pod, those three different version strings were
the evidence. Cross-tenant `/proc` inspection produced the same result: hard boundary
versus soft boundary, side by side.

Agent Sandbox composes with both. A single field — `runtimeClassName: kata` in a
`SandboxTemplate` — is the platform admin's control point. Every `SandboxClaim` from
that template gets VM-level isolation transparently, without developer involvement.

=== When to Recommend Each Technology

[cols="1,2,2",options="header"]
|===
| Situation | Recommendation | Key Signal

| Compliance requirements prohibit customer-managed master nodes
| ARO HCP
| "Show me your master VMs" — empty resource group is the answer

| Multi-tenant workloads with kernel-level isolation requirements
| OpenShift Sandboxed Containers with kata RuntimeClass
| Regulated industries: FSI, government, healthcare

| AI agents executing tool calls or LLM-generated shell commands
| Red Hat Build of Agent Sandbox + kata SandboxTemplate
| Any platform running code interpreters or agentic workflows

| Latency-sensitive or high-density workloads where nested-virt overhead matters
| runc with namespace isolation
| Benchmark first; kata adds cold-start latency without a warm pool
|===

=== Three Discovery Questions

Use these in a customer meeting:

. *"Do your compliance requirements prohibit customer-managed master nodes?"*
  This opens the ARO HCP conversation. The managed control plane model and FSI/government
  identity binding story follow naturally.

. *"Do you run multi-tenant workloads where kernel-level isolation is a hard requirement?"*
  Ask what their current isolation story is. Namespace isolation is usually the answer,
  and that is a soft boundary.

. *"Are you deploying AI agents that need sandboxed code execution?"*
  This is the emerging conversation in regulated industries. Agent Sandbox combined with
  OpenShift Sandboxed Containers gives platform teams a single API surface with
  hardware-enforced isolation.

  --for=condition=InProgress=false --timeout=1200s
